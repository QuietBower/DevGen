    serial: 8250: validate iomem_base in serial8250_verify_port()
    
    This commit addresses a slab-use-after-free caused by an unhandled page
    fault in mem_serial_in(). It prevents userspace from changing io_type
    to/from memory-mapped types or altering the iomem_base of an existing
    memory-mapped port via the TIOCSSERIAL ioctl.

    This is a pre-existing issue, but does this check miss the UPIO_AU and
    UPIO_TSI types?
    
    Looking at serial8250_request_std_resource(), UPIO_AU and UPIO_TSI are
    treated identically to UPIO_MEM for ioremap operations:
    
    drivers/tty/serial/8250/8250_port.c:serial8250_request_std_resource() {
    	...
    	case UPIO_AU:
    	case UPIO_TSI:
    	...
    }
    
    Could a user with CAP_SYS_ADMIN still trigger the page fault by setting
    io_type to UPIO_AU or UPIO_TSI, since they appear to bypass this new
    validation?
    
    +> +		if (ser->io_type != port->iotype ||
    +> +		    (unsigned long)ser->iomem_base != port->mapbase)
    +> +			return -EINVAL;
    
    This isn't a bug introduced by this patch, but should this validation also
    ensure that iomem_reg_shift and type remain unmodified?
    
    If a user leaves iomem_base and io_type unchanged to bypass the new
    validation block, they might still maliciously increase iomem_reg_shift.
    When mem_serial_in() calculates the offset:
    
    drivers/tty/serial/8250/8250_port.c:mem_serial_in() {
    	...
    	offset = offset << p->regshift;
    	return readb(p->membase + offset);
    }
    
    Could the unchecked regshift value push the offset far beyond the bounds
    of the ioremapped membase region, potentially resulting in an out-of-bounds
    MMIO access?
