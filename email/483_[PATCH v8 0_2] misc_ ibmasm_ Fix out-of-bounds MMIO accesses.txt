    This patch adds validation to the Message Frame Address (MFA) before using
    it as an offset to prevent out-of-bounds MMIO access. It also adjusts the
    size passed to ibmasm_receive_message() to fix a 12-byte out-of-bounds read
    and drops invalid MFAs on the send path to prevent wild DMA.

    This is a pre-existing issue, but does this code unconditionally write an
    out-of-bounds MFA back to the hardware?
    
    The patch correctly prevents the driver from dereferencing an out-of-bounds
    Message Frame Address (MFA). However, immediately following this block in
    ibmasm_interrupt_handler(), the driver still unconditionally executes:
    
    	set_mfa_outbound(base_address, mfa);
    
    Writing the out-of-bounds MFA back to the hardware's outbound queue free pool
    allows the hardware to use that invalid address for subsequent messages, which
    could lead to wild DMA and host memory corruption. Should the same
    drop-on-invalid logic used in the inbound path be applied here?
    
    
    While reviewing this patch, I noticed a couple of other pre-existing issues
    in drivers/misc/ibmasm/command.c related to the error handling path.
    
    This is a pre-existing issue, but is there an unbounded mutual recursion
    between do_exec_command() and exec_next_command()?
    
    drivers/misc/ibmasm/command.c:do_exec_command() {
    	...
    	if (ibmasm_send_i2o_message(sp)) {
    		sp->current_command->status = IBMASM_CMD_FAILED;
    		wake_up(&sp->current_command->wait);
    		command_put(sp->current_command);
    		exec_next_command(sp);
    	}
    }
    
    drivers/misc/ibmasm/command.c:exec_next_command() {
    	...
    	spin_lock_irqsave(&sp->lock, flags);
    	sp->current_command = dequeue_command(sp);
    	if (sp->current_command) {
    		command_get(sp->current_command);
    		spin_unlock_irqrestore(&sp->lock, flags);
    		do_exec_command(sp);
    	...
    }
    
    If ibmasm_send_i2o_message() fails continuously (e.g., due to a full queue or
    invalid MFA) and userspace has queued many commands, do_exec_command() will
    synchronously call exec_next_command(), which dequeues the next command and
    calls do_exec_command() again. With a deep enough command queue, this mutual
    recursion could exhaust the limited kernel stack.
    
    
    This is a pre-existing issue, but does the error path in do_exec_command()
    have a race condition leading to a NULL pointer dereference?
    
    In do_exec_command(), sp->current_command is accessed without holding
    sp->lock:
    
    drivers/misc/ibmasm/command.c:do_exec_command() {

    	if (ibmasm_send_i2o_message(sp)) {

    	...

    sets sp->current_command to NULL if the queue is empty:
    
    drivers/misc/ibmasm/command.c:exec_next_command() {
